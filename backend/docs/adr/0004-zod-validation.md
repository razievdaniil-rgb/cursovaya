# ADR 0004. Zod как единственный способ валидации входных DTO

- Дата: 2026-10-31
- Статус: принято

## Контекст

`CLAUDE.md` допускает Zod или class-validator, но требует выбрать один подход и
применять его последовательно. Frontend уже использует Zod вместе с
React Hook Form (`@hookform/resolvers`).

## Решение

1. Все входные данные (body, query, params) описываются схемами Zod в файлах
   `*.schema.ts` рядом с контроллером.
2. Валидация выполняется общим `ZodValidationPipe` из `src/common/`.
   Ошибка валидации превращается в ответ RFC 9457 Problem Details с типом
   `https://medizdeliya.local/problems/validation-failed` и полем `errors`
   с разбивкой по путям.
3. Типы DTO выводятся из схем через `z.infer`, отдельных классов DTO нет.
4. Для OpenAPI схемы Zod конвертируются в JSON Schema; Swagger-декораторы на
   телах запросов не дублируют валидацию.
5. class-validator и class-transformer в зависимости не добавляются, чтобы не
   было двух конкурирующих источников правил валидации.

## Последствия

- Плюс: одни и те же правила (например, минимальная длина пароля)
  формулируются один раз и читаются одинаково на frontend и backend.
- Плюс: Zod-схемы — обычные значения, их легко переиспользовать в тестах.
- Минус: декораторный OpenAPI NestJS работает хуже; описания запросов
  формируются из конвертированных JSON Schema.
