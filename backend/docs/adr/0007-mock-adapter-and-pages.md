# ADR 0007. Mock-адаптер сохраняется, выбор клиента — через переменные сборки

- Дата: 2026-10-31
- Статус: принято

## Контекст

GitHub Pages публикует только статику. Пока API не размещён публично, демо
должно продолжать работать. При этом UI не должен знать, откуда приходят данные.

## Решение

1. `src/types.ts` остаётся единственным контрактом. Интерфейс `ApiClient`
   расширяется, backend-DTO из NestJS во frontend не импортируются.
2. `src/api/mockApi.ts` **не удаляется**. Он остаётся полноценной реализацией
   `ApiClient` и используется в unit-тестах и в демо на Pages.
3. Добавляется `src/api/httpApi.ts` — та же реализация через `fetch` с
   `credentials: 'include'`.
4. Добавляется `src/api/client.ts`, который экспортирует `apiClient` и выбирает
   реализацию: HTTP, если задан `VITE_API_URL` и `VITE_USE_MOCK_API !== 'true'`,
   иначе mock. Страницы импортируют только `apiClient`.
5. Workflow `deploy-pages.yml` не меняет команду сборки и не задаёт
   `VITE_API_URL`, поэтому Pages автоматически собирается с mock-адаптером.
6. Переход на HTTP-путь выполняется только после того, как он покрыт тестами —
   это условие из `CLAUDE.md`.

## Последствия

- Плюс: демо на Pages продолжает работать на каждом коммите в `main`.
- Плюс: unit-тесты frontend не требуют поднятой базы.
- Минус: две реализации одного интерфейса нужно держать согласованными.
  Защита — общий набор контрактных тестов, запускаемый против обеих.
