# ADR 0006. Производные данные — только во views, не в базовых таблицах

- Дата: 2026-10-31
- Статус: принято

## Контекст

Карточке каталога нужны рейтинг, число отзывов и диапазон цен. Аналитике нужны
доля отечественных изделий и зависимость категорий от импорта. Хранить это
колонками в `products` означает транзитивные зависимости и риск рассинхрона.

## Решение

1. Базовые таблицы остаются нормализованными и являются единственным
   источником истины.
2. Обычные (не материализованные) представления — там, где нужна актуальность
   на момент запроса:
   - `product_rating_view` — средний рейтинг и число **опубликованных** отзывов;
   - `product_price_range_view` — `min`/`max` по действующим на `now()`
     предложениям поставщиков;
   - `product_catalog_view` — карточка каталога поверх двух предыдущих;
   - `problem_products_view` — истекающая или приостановленная регистрация,
     критические отзывы, отсутствие действующих предложений;
   - `organization_dashboard_view` — сохранённые позиции, сравнения, отзывы и
     непрочитанные уведомления.
3. Materialized views — только для аналитики, которая читается часто и терпит
   задержку:
   - `category_import_dependency_view` — доля импортных изделий по категориям;
   - `domestic_share_by_period_view` — доля российских изделий по годам.

   Обе обновляются `REFRESH MATERIALIZED VIEW CONCURRENTLY` после успешного
   `sync_run` и по расписанию. Для `CONCURRENTLY` у каждой есть UNIQUE-индекс.
4. Ни одно materialized view не является единственным хранилищем: удаление и
   пересоздание любой из них не теряет данных.

## Последствия

- Плюс: невозможен рассинхрон рейтинга и реального состава отзывов.
- Плюс: 3НФ не нарушена — производные значения вне базовых отношений.
- Минус: аналитика может отставать от записи до следующего refresh. Для
  государственных отчётов это приемлемо и отражено в ответе API полем
  `refreshedAt`.
