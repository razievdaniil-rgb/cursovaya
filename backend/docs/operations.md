# Запуск и эксплуатация

## Полный стек

Нужны Docker с Compose и два случайных секрета длиной от 32 символов.
Скопируйте корневой `.env.example` в `.env`, задайте `JWT_ACCESS_SECRET`,
`JWT_REFRESH_SECRET` и собственный `POSTGRES_PASSWORD`. Затем из корня:

```sh
docker compose up --build -d --wait
```

Интерфейс: `http://localhost:8080`, API: `http://localhost:8080/api/v1`,
Swagger: `http://localhost:3000/api/v1/docs`. Nginx проксирует `/api/` к API,
поэтому интерфейсу не нужен публичный адрес отдельного сервера. Для внешнего
доступа требуется HTTPS; production refresh-cookie имеет атрибут Secure.

Миграции применяются при старте контейнера API. Системные справочники входят
в миграции: регистрация и реальная загрузка работают без demo seed.
Демонстрационные пользователи, отзывы, цены и четыре изделия автоматически
в production не создаются.

## Первый администратор

Из `backend/` после сборки или внутри контейнера задайте окружение
`ADMIN_EMAIL` и `ADMIN_PASSWORD` (12–128 символов), затем:

```sh
npm run admin:create
```

Для контейнера переменные передаются `docker compose exec -e ADMIN_EMAIL
-e ADMIN_PASSWORD api npm run admin:create`. Команда создаёт только нового
пользователя, никогда не меняет пароль и роли существующего email. Секреты
в вывод не попадают. Пароли/ключи не коммитятся.

## Внешний реестр

Источник: публичный виджет официального сервиса Росздравнадзора
`https://roszdravnadzor.gov.ru/services/misearch`, endpoint:

```text
POST https://elk.roszdravnadzor.gov.ru/public-gateway/registered-med-product/api/v1/med-product/filter-public?page=0&size=500
Content-Type: application/json
{}
```

Контракт виджета не является документированным стабильным API; ответ
валидируется, несовместимые записи фиксируются в журнале. Внешняя доступность
не гарантируется приложением. Сертификаты для доверия к TLS включены в
`backend/certs`; проверка сертификата не отключается.

Авторизованный government/admin запускает загрузку из страницы синхронизации
либо `POST /api/v1/government/sync/registry/run`. Ответ **202** означает только
создание запуска, а не успешный импорт. Журнал и прогресс:
`GET /api/v1/government/sync?source=roszdravnadzor-registry`.

Альтернативная команда из собранного `backend/`:

```sh
npm run registry:sync -- --page-size=500
# Ограниченная проверка; ожидаемый статус partial и exit code 2:
npm run registry:sync -- --page-size=2 --max-pages=1
```

Для запуска с хоста нужны `DATABASE_URL` и заданный **до запуска Node**
`NODE_EXTRA_CA_CERTS`, указывающий на `certs/russian-trusted-ca.pem`.
Повторный обход обновляет записи по внешнему ID; конфликты регистрационных
номеров не объединяют разные записи молча. Отсутствующие сведения остаются
неизвестными, а доли происхождения считают только известные значения.

Номенклатура загружается отдельно через `POST /government/sync/nomenclature/run`.
Версия архива задаётся `NOMENCLATURE_FILE_NAME`; нельзя гарантировать,
что ведомство уже опубликовало файл на первое число текущего месяца.

## Аварийное завершение загрузки

Фоновые загрузки выполняются процессом API, отдельного брокера/очереди нет.
Прогресс сохраняется после каждой страницы. При аварийной остановке запись
остаётся незавершённой, и уникальный частичный индекс запрещает повторный
запуск источника. Автоматически считать старую загрузку умершей нельзя:
источник может отвечать медленно.

Сначала остановите/проверьте все API и CLI-работники этого источника.
Затем оператор может закрыть **конкретный** зависший run в транзакции:

```sql
BEGIN;
UPDATE sync_runs
SET status_id = (SELECT id FROM sync_run_statuses WHERE code = 'failed'),
    finished_at = now(),
    error_message = 'Остановлено оператором после проверки отсутствия работника'
WHERE id = '<UUID проверенного запуска>'::uuid AND finished_at IS NULL;
COMMIT;
```

Счётчики, ошибки и импортированные записи не удаляются. После этого повторите
обход. Перед применением миграции уникальности к существующей базе проверьте,
что у одного источника нет нескольких незавершённых запусков.

## Почта и восстановление пароля

Нужен настроенный HTTPS email API с JSON-контрактом Resend:
`RECOVERY_EMAIL_API_URL`, `RECOVERY_EMAIL_API_KEY`, `RECOVERY_EMAIL_FROM`,
`RECOVERY_RESET_URL=https://<ваш-домен>/auth/recovery`.
Доставка выполняется POST-запросом с `from`, `to`, `subject`, `text` и Bearer
авторизацией. Проверка доставки покрыта подменой транспорта; реальный ключ и
подтверждённый отправитель предоставляются оператором.

Без настройки endpoint восстановления возвращает 503. Токен в логи и ответ
не попадает; ссылка содержит его во fragment `#token=...`. Форма меняет пароль
через `/auth/recovery/confirm`, токен одноразовый даже при параллельных запросах.

## Проверки

Backend: `npm run typecheck`, `npm run lint`, `npm run test:unit`,
`npm run test:integration`, `npm run openapi:export`.
Integration-тесты запускайте на отдельной базе с миграциями и demo seed,
никогда на рабочем зеркале реестра. Они создают и удаляют фикстуры.

Frontend: `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`,
`npm run test:e2e`. Для HTTP smoke соберите с `VITE_API_URL`, задайте
`E2E_API_URL` и `E2E_SEED_PASSWORD`. Сетевой тест внешнего реестра включается
`REGISTRY_NETWORK_TEST=true`; он не является обязательной зависимостью CI.

CI отдельно проверяет миграции/seed, backend, браузерный HTTP-путь и полный
Docker Compose на новой базе без seed. GitHub Pages продолжает собираться
через mock-адаптер и не требует работающего внешнего источника.
