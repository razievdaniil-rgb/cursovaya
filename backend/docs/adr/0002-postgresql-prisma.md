# ADR 0002. PostgreSQL 17 + Prisma с SQL-миграциями под контролем

- Дата: 2026-10-31
- Статус: принято

## Контекст

Нужна реляционная БД в 3НФ с составными первичными ключами, CHECK-ограничениями,
представлениями, materialized views, полнотекстовым поиском и расширением `citext`.
Часть этих возможностей декларативная модель ORM не выражает.

## Решение

1. СУБД — PostgreSQL 17.
2. ORM — Prisma Client для типизированного доступа из NestJS.
3. Миграции — каталог `prisma/migrations` с обычными SQL-файлами:
   - `0000_extensions` — расширения `citext` и `pg_trgm`;
   - `0001_init` — все таблицы, первичные и внешние ключи, UNIQUE, индексы
     (сгенерировано Prisma из `schema.prisma`);
   - `0002_constraints_and_views` — CHECK-ограничения, триггеры
     поискового индекса, views и materialized views (написано вручную).
4. Схема применяется с нуля одной командой: `npm run db:migrate:deploy`.
   Отдельная CI-джоба поднимает чистый PostgreSQL и прогоняет миграции и seed.
5. Enum PostgreSQL и `enum` Prisma **не используем** для справочников. Все
   справочные значения — строки в отдельных таблицах с внешними ключами
   (см. ADR 0003). Enum потребовал бы миграции DDL при каждом новом значении и
   не позволил бы хранить `name`, `sort_order` и прочие атрибуты значения.

## Последствия

- Плюс: полный контроль над DDL, при этом типизированный клиент.
- Плюс: воспроизводимость — `migrate deploy` на пустой базе даёт ту же схему.
- Минус: объекты из `0002` (views, триггеры) Prisma не видит в `schema.prisma`,
  поэтому `prisma migrate dev` их не пересоздаёт автоматически. Защита —
  CI-проверка миграций на чистой базе и явный запрет на `prisma db push`.
- Минус: `tsvector` и `citext` в Prisma описаны как `Unsupported`/`@db.Citext`,
  поисковые запросы идут через `$queryRaw`.
