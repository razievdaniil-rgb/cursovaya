# ADR 0010. Подключение настоящего государственного реестра медицинских изделий

> Уточнение: идентификация по внешнему ID, атомарная история, частичная загрузка
> и фоновый HTTP-запуск описаны в [ADR 0011](0011-production-integrity.md).
> Эти решения заменяют прежнее сопоставление только по регистрационному номеру.

- Дата: 2026-11-01
- Статус: принято
- Заменяет в части реестра: [ADR 0008](0008-registry-provider.md)
- Закрывает открытый вопрос: [ADR 0009](0009-roszdravnadzor-open-data.md)

## Контекст

ADR 0009 оставил открытый вопрос: регистрационные записи реестра публично
недоступны, потому что набор открытых данных № 11 выдаётся только после
авторизации в ЕСИА. Из этого был сделан вывод, что реестр остаётся за
`MockRegistryProvider`.

Вывод оказался неполным. Файловая выгрузка действительно закрыта, но тот же
реестр отдаёт публичный REST API виджета Росздравнадзора:

```
POST https://elk.roszdravnadzor.gov.ru/public-gateway/registered-med-product/api/v1/med-product/filter-public?page=&size=
Content-Type: application/json

{}
```

Пустое тело означает «весь реестр». Авторизация не нужна. Ответ — обычная
пагинация Spring Data (`content`, `totalElements`, `totalPages`, `last`,
`number`), до 1000 записей за запрос. На 2026-11-01 `totalElements` = 81 566.

Условие ADR 0008 («реальный HTTP-provider не реализовывать без официальной
документации и доступа») выполнено наполовину, и это стоит записать прямо:
**доступ есть, официальной документации нет.** Этот API обслуживает виджет на
сайте ведомства, его контракт нигде не описан и выведен из самих ответов.

Правило всё же нарушено сознательно: требование «реестр должен быть
настоящим» поставлено явно, а альтернатива — выдавать демонстрационные
данные за государственный реестр — хуже по всем статьям. Риск недокументированного
контракта принят и ограничен: формат зафиксирован фикстурой из настоящих
ответов и тестами, которые покажут расхождение, а не замолчат его.

### Препятствие: сертификат национального УЦ

`elk.roszdravnadzor.gov.ru` предъявляет сертификат, выданный национальным
удостоверяющим центром Минцифры. Этого корня нет в наборе доверенных
сертификатов Node, поэтому любое обращение падает с `fetch failed`, а
настоящая причина — `unable to verify the first certificate` — оказывается в
`cause` и в журнал не попадает.

Вариантов было три:

1. отключить проверку сертификата (`NODE_TLS_REJECT_UNAUTHORIZED=0`);
2. установить корень Минцифры в хранилище доверенных сертификатов системы;
3. добавить корень только процессу backend.

## Решение

1. **Реестр подключается как настоящий источник.**
   `RoszdravnadzorRegistryProvider` сообщает `isReal: true`,
   `RegistrySyncService` грузит записи в те же `products` и `manufacturers`,
   что и демонстрационная загрузка: реестр — это и есть каталог.

2. **`MockRegistryProvider` остаётся и не выдаётся за реальный.** Он
   по-прежнему обслуживает `POST /government/sync/run` и демонстрацию на
   GitHub Pages (ADR 0007), и `GET /government/sync` показывает источники
   раздельно: `mock-registry` с `isReal: false`, `roszdravnadzor-registry` и
   `roszdravnadzor-nomenclature` с `isReal: true`. Признак берётся из
   описания провайдера, а не из таблицы: «подключён настоящий источник» —
   свойство кода, и подменить его записью в базе нельзя.

3. **Доверие к корню Минцифры — только у процесса backend.** Выбран третий
   вариант: `NODE_EXTRA_CA_CERTS=certs/russian-trusted-ca.pem`.

   - Отключать проверку нельзя: это снимает защиту от подмены для всех
     соединений процесса, включая обращения к базе и к любым другим сервисам.
     Рабочая интеграция не стоит выключенного TLS.
   - Установка корня в систему решила бы задачу, но дала бы этому УЦ право
     подтверждать сертификаты **для любого домена** на всей машине, а не
     только для `elk.roszdravnadzor.gov.ru`. Это несоразмерно задаче.
   - `NODE_EXTRA_CA_CERTS` добавляет корень к доверенным, **не отключая
     проверку**, и действует только на тот процесс, которому переменная
     передана.

   Корень и промежуточный сертификат лежат в `backend/certs/`, скачаны с
   официального `https://gu-st.ru/content/lending/`; происхождение, отпечаток
   SHA-256 и способ проверки описаны в `backend/certs/README.md` — вместе с
   тем, что доверие корню всё равно распространяется на любой домен в пределах
   этого процесса.

   Без переменной загрузка падает, и провайдер пишет в журнал не
   «fetch failed», а инструкцию, что именно нужно передать процессу.

4. **Полей, которых в источнике нет, мы не выдумываем.** Реестр даёт
   регистрационный номер, название, статус, даты, правовую систему,
   производителя строкой с адресом и идентификатор ФРНСИ. Проверка 1566
   записей из разных частей реестра показала, чего в нём нет:

   | Поле источника | Заполнено | Что с ним делаем |
   | --- | --- | --- |
   | `riskClassId` | 0–3 % | `products.risk_class_id` стал NULLABLE |
   | `modelsDescription` | 0–3 % | отдельная колонка, NULL по умолчанию |
   | `nomClassifierMedicalRfIds` | 27–42 % | разбирается, но не связывается — см. ниже |
   | категория | нет вообще | `products.category_id` стал NULLABLE |
   | происхождение | нет вообще | `products.origin_type_id` стал NULLABLE |
   | страна производителя | нет вообще | `manufacturers.country_id` стал NULLABLE |

   Это сознательный размен: обязательность внешнего ключа ослаблена, зато в
   базе нет вымышленных значений. Выводить страну из строки адреса или
   назначать всем записям класс риска «по умолчанию» означало бы приписать
   государственному реестру сведения, которых в нём нет. Пустое поле честнее
   правдоподобной выдумки.

   Про `nomClassifierMedicalRfIds` отдельно. Поле выглядит как готовая связь
   с номенклатурной классификацией из ADR 0009, но ею не является:
   реестр отдаёт 19-значные идентификаторы вида `3306965748378768392`, а
   номенклатура хранится по своим кодам вида `100260` — это шестизначное
   число. Сопоставить их без таблицы соответствия нельзя, а подобрать
   «похожий» код означало бы приписать изделию чужой вид. Поэтому значения
   разбираются провайдером и доступны в `RegistryEntry.nomenclatureIds`, но
   `products.nomenclature_type_id` загрузка реестра не заполняет.

   Миграция: `20261101170000_real_registry`. Там же появляются
   `products.external_registry_id` (UNIQUE, идентификатор записи в реестре),
   `products.frnsi_id`, `products.legal_system` и
   `manufacturers.actual_address`.

5. **Аномальные даты сохраняются как опубликованы.** В реестре есть записи,
   где срок действия удостоверения истекает раньше даты регистрации:
   например, `ФС 01012002/2879-06` — регистрация 07.02.2006, окончание
   07.02.2000. Похоже на опечатку в годе на стороне источника; таких записей
   около трёх на тысячу.

   Прежний `products_registration_period_check` их отвергал, и настоящие
   записи реестра просто терялись. Правило сохранено для записей, которые
   заводим мы сами, и снято для загруженных из реестра — у них заполнен
   `external_registry_id` (миграция `20261101180000_registry_date_anomalies`).
   Каждая такая запись попадает в `sync_run_errors` с кодом
   `REGISTRY_DATE_ANOMALY`, то есть остаётся видимой в журнале загрузок.

   Зеркало государственного реестра обязано показывать то, что в нём
   опубликовано; молча «починенная» дата — это искажение.

6. **Производные представления приведены в соответствие с данными.**
   Необязательные внешние ключи сломали два представления, написанные под
   seed, где все поля заполнены (миграция
   `20261101190000_views_tolerate_registry_gaps`):

   - `product_catalog_view` соединял `countries`, `product_categories`,
     `risk_classes` и `product_origin_types` внутренним JOIN, поэтому запись
     с пустым значением из каталога **исчезала целиком**. После загрузки
     реестра так пропали бы все 80 с лишним тысяч записей — интеграция
     оказалась бы бесполезной. Соединения стали внешними.
   - `category_import_dependency_view` и `domestic_share_by_period_view`
     считали доли от всех изделий. С записями реестра, где происхождения нет,
     доля отечественных изделий сползла бы почти к нулю — не потому, что
     импорта стало больше, а потому, что знаменатель вырос за счёт записей,
     про которые ничего не известно. Теперь доля считается по изделиям с
     известным происхождением, а остальные выведены отдельной колонкой
     `unknown_origin_products` и отдаются в API: неполнота данных видна, а не
     спрятана в знаменателе.
   - `GET /catalog/filters` строил список производителей через внутренний
     JOIN со странами, поэтому ни один производитель из реестра в фильтр не
     попадал. Соединение стало внешним, `country` в ответе может быть `null`.

7. **Неизвестный статус — повод пропустить запись, а не придумать статус.**
   Источник отдаёт пять кодов, и все они отображаются в справочник
   `registry_statuses`:

   | Код источника | Название в реестре | Код справочника |
   | --- | --- | --- |
   | `active` | Действует | `active` |
   | `deadline_has_expired` | Срок действия истек | `expired` |
   | `invalid` | Недействительно | `invalid` |
   | `cancelled` | Отменено | `cancelled` |
   | `suspended` | Приостановлено | `suspended` |

   Пятый код выяснился не сразу, и это стоит записать: в первых проверенных
   выборках `invalid` не встретился, а на полной загрузке под него попало
   9 796 записей — около 12 % реестра. Все они были пропущены, и загрузка
   честно закончилась статусом `partial` с объяснением в журнале. То есть
   отображение статусов выведено из полного обхода реестра, а не из выборки:
   выборка здесь обманывает, потому что записи в ответе сгруппированы и
   редкие состояния в первые страницы не попадают.

   Код, которого в отображении нет, означает, что реестр ввёл новое
   состояние, смысл которого нам неизвестен. Такая запись пропускается, а
   причина пишется в `sync_run_errors` с кодом `ENTRY_IMPORT_FAILED`, и
   загрузка завершается статусом `partial`. Одна плохая запись не рвёт
   загрузку целиком — и, как показал этот случай, именно так обнаруживается
   расхождение с источником.

8. **Загрузка не зависит от демонстрационного seed.** Справочные значения,
   без которых не завести запуск (`sync_run_statuses`) и статусы реестра,
   создаются самой загрузкой. Зеркало реестра должно подниматься на базе, где
   применены только миграции.

9. **Сорванный обход доигрывается повторным запуском.** Полный обход — это
   164 запроса подряд примерно за двадцать минут, и источник за это время
   успевает и разорвать соединение («other side closed»), и перестать
   отвечать на минуту. Поэтому страница запрашивается до шести раз с
   возрастающей паузой (2, 6, 18, 54, 60 секунд — около двух с половиной
   минут терпения). Первая версия с четырьмя попытками теряла загрузку на
   102-й странице из 164: 26 секунд терпения на минутный провал связи не
   хватает.

   Если обход всё же сорвался, повторный запуск продолжает работу: записи
   сопоставляются по регистрационному номеру, уже загруженные обновляются, а
   недостающие создаются. Отдельного состояния «докачки» не нужно — его роль
   играет естественный ключ.

10. **Естественный ключ — регистрационный номер.** Запись без `noRu`
    отбрасывается провайдером: без номера её не с чем сопоставлять при
    повторной загрузке. Повторная загрузка обновляет записи и создаёт событие
    в `registry_status_history` только при фактической смене статуса — иначе
    история росла бы на каждую загрузку, не сообщая ничего нового.

    Статус изделия и событие истории пишутся одной транзакцией, как и при
    демонстрационной загрузке: статус без события — потерянный след загрузки,
    событие без статуса — расхождение между `products` и историей.

## Проверка

- Полная загрузка всех 81 566 записей выполнена на пустой базе с применёнными
  миграциями и без seed.
- Интеграционные тесты (`test/registry.e2e.spec.ts`) идут на локальной
  фикстуре `test/fixtures/registry-page.json`, собранной из настоящих записей
  реестра и дополненной краевыми случаями: аномальные даты, пустой `noRu`,
  отсутствующий производитель, статус `invalid` и неизвестный код статуса.
  Отдельные тесты проверяют, что запись реестра без категории видна в
  каталоге и что её производитель без страны попадает в справочник фильтров:
  именно это ломалось внутренними JOIN.
- Обращение к сети проверяется отдельным тестом, который включается
  переменной `REGISTRY_NETWORK_TEST=true`; ему нужен и
  `NODE_EXTRA_CA_CERTS`. CI его не запускает: там нет корня Минцифры, и
  сборка не должна падать из-за недоступности сайта ведомства.

## Последствия

- Плюс: каталог строится на настоящем государственном реестре, а не на
  четырёх демонстрационных изделиях. Требование CLAUDE.md «не заявлять о
  реальном подключении, пока внешний источник действительно не подключён»
  выполняется в сильную сторону: источник подключён, и это подтверждается
  загрузкой.
- Плюс: запуск без доверия к корню даёт понятное сообщение, а не «fetch
  failed».
- Минус: у источника нет официальной документации. Контракт выведен из
  ответов, поэтому изменение формата сломает загрузку. Защита — фикстура и
  тесты, которые покажут расхождение.
- Минус: три внешних ключа `products` и страна производителя стали
  необязательными. Карточка и фильтры должны работать с пустыми значениями, а
  не рассчитывать на заполненность.
- Минус: запуск backend требует дополнительной переменной окружения. Она
  прописана в `docker-compose.yml` и в README; без неё работает всё, кроме
  загрузки реестра.
- Открытый вопрос: класс риска и категория в реестре отсутствуют. Если они
  понадобятся как фильтры для всего каталога, источник придётся искать
  отдельно — из этого API их взять неоткуда.
- Открытый вопрос: связь записей реестра с номенклатурной классификацией.
  Реестр ссылается на виды своими 19-значными идентификаторами, несовместимыми
  с кодами классификатора; нужна таблица соответствия, которой у нас нет.
